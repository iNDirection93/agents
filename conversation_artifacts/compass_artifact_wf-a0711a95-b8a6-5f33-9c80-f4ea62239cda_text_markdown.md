# Development-Focused Agent Graphs: Reference Examples a Small Squad Can Copy

## TL;DR
- **For a 3–6 person squad, the highest-leverage starting point is not a custom harness — it is a spec-driven design graph (GitHub Spec Kit or Kiro's own requirements→design→tasks flow) plus a bounded generator→reviewer loop for build work.** Both are copyable today with real config; add orchestration frameworks (LangGraph) only when you need the durable checkpointing, replay, and inspection that Kiro's opaque sub-agents cannot give you.
- **Kiro's native sub-agent DAG is real and capable (parallel stages, dependency ordering, review loops via internal `target`/`trigger`/`max_iterations`), but it is agent-planned at runtime with no authored graph file, no per-stage checkpoint/replay, and only summaries crossing edges** — exactly the opacity the user complains about. The escape hatch is a custom harness driving `kiro-cli chat --no-interactive` nodes, but that is currently hampered by Kiro's lack of machine-readable output (GitHub issues #5423, #9066).
- **The dominant, best-documented topologies for dev work are orchestrator-worker (Anthropic Research), evaluator-optimizer / reflection loops (LangGraph, ADK llm-auditor), and supervisor/handoff (langgraph-supervisor, langgraph-swarm). The strongest counter-evidence — Cognition's "Don't Build Multi-Agents" — is that for most coding work you should prefer a single agent with read-only sub-agents and excellent context engineering.** Start narrow, widen only when the simple version measurably hurts.

## Key Findings

1. **Design-work graphs are where multi-agent structure pays off most safely.** Requirements/design/ADR/critique work is breadth-first, artifact-producing, and tolerant of parallel exploration — the exact profile where Anthropic found a multi-agent system (Claude Opus 4 lead + Claude Sonnet 4 subagents) "outperformed single-agent Claude Opus 4 by 90.2% on our internal research eval," with token usage explaining roughly 80% of the performance variance. Build-work graphs are riskier: Cognition's Principle 2 is blunt — "Actions carry implicit decisions, and conflicting decisions carry bad results" — so parallel implementation agents tend to disagree on style and edge cases.

2. **The canonical reusable patterns and where they fit:**
   - **Orchestrator-worker (fan-out/gather):** design research, breadth-first spec exploration. Anthropic Research is the reference.
   - **Evaluator-optimizer / reflection / player-coach:** design critique, code review loops, test-fix loops. LangGraph reflection, ADK llm-auditor, Kiro player/coach.
   - **Generator-discriminator / debate / council:** competing design proposals judged/synthesized. LangGraph multiple-generators + LLM-as-judge.
   - **Supervisor / hierarchical teams:** a lead routes to specialists. langgraph-supervisor.
   - **Handoff / swarm:** peer agents pass control. langgraph-swarm, OpenAI Agents SDK handoffs.
   - **Plan-and-execute:** decompose plan → parallel tasks. Kiro spec tasks, Deep Agents, spec-kit.
   - **Human-in-the-loop gate:** approval between phases. LangGraph interrupts, Kiro spec review, Spec Kit `/analyze`.

3. **State should cross edges as durable artifacts (files, git branches, spec docs), not just summaries or full context.** Every credible source converges here: Anthropic persists the lead plan to Memory to survive the 200k-token limit; Cognition insists on sharing full context/traces; Kiro sub-agents pass only summaries (a limitation); the spec-driven tools write requirements.md / design.md / tasks.md to disk. Artifacts-on-disk is the approach that held up and is also what makes runs inspectable after the fact.

4. **Observability/checkpointing is the deciding factor between Kiro-native and a harness.** Kiro gives a live execution monitor (Ctrl+G) and session checkpoints/rewind, but no per-stage DAG replay and only summaries across edges. LangGraph gives per-superstep checkpointing, time-travel debugging, and resume-from-failure; pair with LangSmith/Langfuse/Laminar and OTel GenAI tracing. Temporal gives true durable execution (journaled replay) as a substrate under any framework.

5. **Documented failure modes are consistent:** graphs too wide (Anthropic's early agents "spawning 50 subagents for simple queries, scouring the web endlessly for nonexistent sources, and distracting each other with excessive updates"), over-decomposition, context loss across edges, merge conflicts from parallel build agents, review loops that never converge (hence bounded iterations), and 4×–15× token cost blowups. The mitigations are bounded iteration caps, git-worktree isolation, read-only sub-agents, and starting with one agent.

## Details

### SECTION 1 — DESIGN-WORK GRAPHS (architecture & specification phase)

**1a. Spec-driven development flow — Kiro-native (the user already has this).**
Kiro's core spec workflow is a linear design graph: *requirements → design → tasks*, each an inspectable artifact. This is Kiro's most valuable design-work graph and it is directly copyable via `/spec new` in the CLI or the IDE. It maps 1:1 onto the classic requirements/design/ADR flow. Kiro on the web adds inline review and multi-user collaboration on specs. Because each phase produces a durable markdown artifact, this flow is inherently more inspectable than Kiro's runtime sub-agent DAG. Source: kiro.dev/blog/one-agent; kiro.dev docs.

**1b. GitHub Spec Kit — framework-based, agent-agnostic (strongest copyable design graph).**
`github/spec-kit` (install: `uv tool install specify-cli`) implements Spec-Driven Development as an explicit sequence of slash commands: `/speckit.specify` → `/speckit.plan` → `/speckit.tasks` → `/speckit.analyze` (a cross-artifact consistency/coverage gate, "unit tests for English") → `/speckit.implement`. Its docs list 20+ supported agents — including GitHub Copilot, Claude Code, Cursor, Windsurf, Gemini CLI, Codex CLI, Amazon Q Developer, **Kiro**, Amp, Roo Code, and Junie — plus a `--ai generic` mode for unsupported agents, so it composes cleanly with the user's Kiro stack. The `/analyze` step is a built-in human-in-the-loop quality gate. This is the single best "study-and-copy" artifact for design work: real templates, real scripts, and a constitution file for persistent project context. Repo: github.com/github/spec-kit; docs: github.github.com/spec-kit.

**1c. Competing proposals + judge/synthesizer (generator-discriminator / council) — framework-based.**
For tradeoff analysis and ADRs where you want multiple competing designs, the reference implementations are LangGraph's evaluator-optimizer and reflection templates: multiple generator nodes produce competing proposals, a judge/critic node scores or synthesizes. `langchain-ai/langgraph-reflection` is a concrete repo: a main graph produces output, a judge graph (LLM-as-judge, e.g. via `create_llm_as_judge`) evaluates and either approves or returns a critique that loops back. The production-hardening advice from LangSmith eval guides is to run the judge at `temperature=0` with explicit binary pass/fail criteria and majority-vote over 3 runs to reduce judge variance. Repo: github.com/langchain-ai/langgraph-reflection.

**1d. Design critique loop — ADK llm-auditor (framework-based, Google).**
`google/adk-samples` includes **llm-auditor**, which "audits LLM responses using critic and reviser sub-agents" in a `SequentialAgent` workflow — a clean, runnable critic→reviser design-critique graph. ADK's workflow primitives (`SequentialAgent`, `ParallelAgent`, `LoopAgent`) are purpose-built for design graphs. Repo: github.com/google/adk-samples (python/agents/llm-auditor; also a Go port).

**1e. Orchestrator-worker for breadth-first design research — the Anthropic reference.**
Anthropic's multi-agent research system is the best-documented orchestrator-worker graph: a Lead Researcher plans, saves its plan to Memory (to survive the 200k-token context limit), spawns 3–5 subagents in parallel each with its own context window (and subagents use 3+ tools in parallel), and a separate citation pass runs at the end — cutting research time by up to 90% for complex queries. It beat single-agent Claude Opus 4 by 90.2% on their internal research eval, at ~15× the token cost of a chat. Directly applicable to "explore the design space / survey prior art / gather requirements from many sources" work. Example prompts are open-sourced in `anthropics/anthropic-cookbook` (patterns/agents/prompts). Source: anthropic.com/engineering/multi-agent-research-system; simonwillison.net writeup (2025/Jun/14).

### SECTION 2 — BUILD-WORK GRAPHS (implementation phase)

**2a. Kiro sub-agent DAG — Kiro-native (what the user already runs; here is exactly what it is).**
Kiro sub-agents support DAGs where "the main agent plans the full task graph upfront, then executes in the right order — running independent tasks in parallel and waiting for dependencies." **Critical detail confirmed from the docs:** the DAG is *planned by the agent at runtime from plain-language instructions* — there is **no authored graph file or schema**, and task graphs "cannot be modified during execution." Review loops are real and use three internal parameters the agent attaches to a stage: `target` (stage to re-run), `trigger` (text like `NEEDS_CHANGES` that fires the loop; must be ≥4 chars), and `max_iterations` (must be ≥1, capped at 10 regardless of what is requested). Constraints: a stage cannot loop to itself; mutual loops A↔B are rejected. Up to four sub-agents run at once. When the trigger fires, the target re-runs "with that stage's feedback as context," and a re-run stage's result is "annotated with the number of iterations used." **State across edges is summaries only** ("Summaries are returned to the main agent automatically"). Review loops shipped in Kiro CLI v2.5 (May 2026). What you *do* author is per-agent config plus a `toolsSettings.subagent` access block (`availableAgents`, `trustedAgents` glob patterns; an orchestrator must include `subagent` in its `tools`). Sources: kiro.dev/docs/custom-agents/subagents; kiro.dev/docs/cli/chat/subagents; kiro.dev/changelog/cli/2-5.

The custom-agent config schema itself (`.kiro/agents/*.json` or `*.md` with YAML frontmatter) supports: `name`, `description` (used for auto-selection of sub-agents), `prompt` (inline text or `file://` import, e.g. `"prompt": "file://./migrator-agent.md"` with relative paths resolved from the config file's directory), `tools`, `allowedTools` (usable without a prompt; supports globs but not `"*"`), `toolAliases` (remap MCP naming collisions), `permissions.rules` (capability/match/effect with deny-overrides), `resources` (`file://`, `skill://`, `knowledgeBase`), `hooks` (CLI only), `model`, `keyboardShortcut`, and `welcomeMessage`. Source: kiro.dev/docs/custom-agents/configuration-reference.

**2b. Kiro player/coach — Kiro-native, real repo (a copyable build+review loop).**
Ricardo Sueiras (AWS) built a three-agent Kiro setup: **orchestrator → player (does the work) → coach (reviews against eval criteria)**, each a `.kiro/agents/*.json` with prompts in `.kiro/shared/*.md`. Layout: `coach.json`, `orch.json`, `player.json` + `COACH.md`, `ORCH.md`, `PLAYER.md`. He used different models for player vs coach and a shared learnings file, and started the workflow with `kiro-cli --agent orch`. **Honest lessons:** hanging on started services and port conflicts; files created in unexpected places; occasional one-shotting instead of decomposing; hard to prove the coach improved output without a baseline; and cost — one player/coach iteration burned 4.3 Kiro credits vs <1 credit for one-shot vibe coding. He noted a current constraint that sub-agents can only auto-use a subset of tools (no MCP/web calls at the time), and concluded he might move to Strands Agents for more control. Repo: github.com/094459/kiro-player-coach.

**2c. Kiro headless in CI — Kiro-native harness building block.**
Kiro CLI runs headless: set `KIRO_API_KEY`, run `kiro-cli chat --no-interactive --trust-tools=read,grep "..."`. A published pattern (Ashish Kasaudhan) wires four GitHub Actions workflows to three purpose-built `.kiro/agents/*.json` definitions (e.g. a `code-reviewer.json` triggered on push). This is the seam a custom harness would drive as graph nodes. **But the harness gap is real:** issue #5423 requests `--output-format json` plus a `--progress-file` NDJSON event stream (still open, "pending Kiro team response"); issue #9066 requests exposing the session ID in headless mode for resume/audit (currently there is no machine-readable way to get it). Until those land, driving Kiro as harness nodes means parsing ANSI/text output and you cannot cleanly resume or trace a headless run. Sources: kiro.dev/blog/introducing-headless-mode; github.com/kirodotdev/Kiro/issues/5423 and /9066.

**2d. Parallel-migration fan-out — Kiro-native, real showcase.**
A DEV Community showcase (dvddpl) used Kiro spec-driven development + custom sub-agents to migrate files across 30+ repos. Key practical lesson: Kiro's IDE authors agents in Markdown, but sub-agent invocation and `kiro-cli` startup need JSON, so he writes the agent in Markdown-with-frontmatter and a JSON wrapper that imports the prompt via `"prompt": "file://migrator-agent.md"`. Also: the first spec task tried to write a script for later tasks to consume, which broke parallel orchestration — a concrete over-decomposition failure. Source: dev.to/dvddpl Kiro showcase.

**2e. Claude Code subagent orchestration — framework/CLI-based, huge community corpus.**
Claude Code subagents are markdown files with YAML frontmatter in `.claude/agents/`; the parent conductor delegates and subagents cannot spawn subagents. Best copyable collections: `VoltAgent/awesome-claude-code-subagents` (100+ agents incl. a `09-meta-orchestration/agent-organizer`), `hesreallyhim/a-list-of-claude-code-agents` (curated with judgment), and Seth Hobson's collection. The best-fit build-work pattern is the **parallel review panel**: run style-checker, security-scanner, and test-coverage subagents on the same diff, parent synthesizes verdicts. Practitioner reports are candid about cost ("Sub Agents — Burn Out Your Tokens": same token pool, so more speed = faster burn) and value (one developer escaped a single-agent failure loop by decomposing into 12 tasks across 5 phases). Sources: docs.anthropic.com/en/docs/claude-code/sdk/subagents; the VoltAgent and hesreallyhim repos.

**2f. Git-worktree isolation for parallel build agents — the standard safety mechanism.**
The consensus fix for merge conflicts from parallel build agents is one git worktree per agent: each agent gets its own branch + directory sharing one `.git`, plus DB branching and port isolation. Claude Code has first-class support (`--worktree`/`-w`, or `isolation: worktree` in a subagent's frontmatter). Scott Chacon/GitButler's "Grit" (rewriting Git in Rust with agents) is the most publicly documented large-scale parallel-agent project. This is the mechanism a small squad should adopt before widening any build fan-out. Sources: code.claude.com/docs/en/worktrees; GitButler blog.

**2g. Supervisor / swarm / plan-execute — framework-based building blocks.**
`langchain-ai/langgraph-supervisor-py` (central supervisor routes to specialists; note LangChain now recommends the tool-based supervisor pattern directly for more context-engineering control) and `langchain-ai/langgraph-swarm-py` (decentralized handoff; remembers last active agent; compile with a checkpointer for durability) are the canonical reusable topologies. `von-development/awesome-LangGraph` catalogs production starter kits with the six patterns (Supervisor, Swarm, HITL, Structured Output, Research, RAG). Deep Agents (planning + subagents + filesystem) is the higher-level option; GPT Researcher migrated from a hardcoded LangGraph pipeline to Deep Agents so planning emerges in the harness rather than being hardcoded in the graph. Repos linked above.

### SECTION 3 — OBSERVABILITY, CHECKPOINTING & DURABILITY (the user's priority)

- **Kiro-native:** live execution monitor via Ctrl+G ("crew monitor" — inspect each subagent's activity in a focused panel), Ctrl+X for task progress. Session-level checkpoints snapshot files Kiro modifies and rewind conversation context; rewind forks the conversation into a new session; an experimental `/checkpoint` CLI command set (init/list/diff/restore) exists. **Gaps:** checkpoints do NOT track MCP/shell/manual edits; there is no per-stage DAG replay; edges carry summaries only. This is the core of the user's complaint and it is accurate.
- **LangGraph:** per-superstep checkpointing keyed by thread, durable execution ("resume from exactly where they left off"), human-in-the-loop by inspecting/modifying state mid-run, and time-travel debugging in LangGraph Studio (set breakpoints, modify state, resume from a checkpoint). This is the strongest agent-native inspection/replay story and the direct answer to Kiro's opacity.
- **Tracing backends (2026):** LangSmith (tightest LangChain/LangGraph fit, OTel support added 2026, closed-source, seat-priced), Langfuse (open-source MIT, now part of ClickHouse; prompt-centric + evals), Laminar (open-source, OTel-native, built for long-running agents; transcript view, SQL over traces, session replay), Arize Phoenix (OTel/OpenInference), Braintrust and W&B Weave (eval-first, partial OTel). Instrument with OpenTelemetry GenAI semantic conventions (agent/workflow/tool/model spans) for portability — but note these `gen_ai.*` attributes are still marked "Development" in the spec (v1.41), so names can change.
- **Durable execution substrate:** Temporal journals every step and replays to reconstruct state after a crash; its OpenAI Agents SDK integration reached GA on **23 March 2026** ("As of March 23rd, 2026, the integration between the OpenAI Agents SDK and Temporal's Python SDK is now Generally Available"). Also in this space: DBOS, Restate, Inngest, Cloudflare Workflows, AWS Lambda Durable Functions (Dec 2025), Microsoft Durable Task for AI agents (April 2026). For a small squad this is likely overkill unless runs span hours or need guaranteed crash recovery.
- **Kiro Crew (AWS, Apache 2.0, ~v0.1.2):** the persistent workspace around Kiro CLI, using Agent Client Protocol; "long-running tasks move through checkpoints, validation, and retries automatically," with signed audit logs and an OS sandbox. Importantly, **AWS open-sourced the orchestration layer but explicitly kept the agent harness proprietary** (VP Deepak Singh: "We are not open sourcing the harness"). So Crew improves observability/governance but does not remove the runtime opacity. Ships apps: DevFleets (worktree management), Task Runner, Issue Radar; plus an App SDK. Repo: github.com/kirodotdev/KiroCrew.

### SECTION 4 — FAILURE MODES & ANTI-PATTERNS (be honest about overkill)

- **The strongest skeptic: Cognition's "Don't Build Multi-Agents" (Walden Yan).** For coding specifically, Principle 2 states "Actions carry implicit decisions, and conflicting decisions carry bad results"; the reliable pattern is a single root agent delegating isolated, read-only sub-tasks to sandboxed sub-agents that "never share machines, never collaborate interactively." Cognition tried giving Devin an MCP to spawn/message other Devins and got "a really chaotic world." Their April 2026 follow-up ("Multi-Agents: What's Actually Working") softens this — "we've found a narrower class of patterns that do [work]: setups where multiple agents contribute intelligence to a task while writes stay single-threaded… most multi-agent setups in the world are limited to 'readonly' subagents" — but still calls unstructured swarms "mostly a distraction."
- **Anthropic's own reported failures:** early agents "spawning 50 subagents for simple queries, scouring the web endlessly for nonexistent sources, and distracting each other with excessive updates," and duplicated work — "one of Anthropic's early systems had a subagent investigating the 2021 automotive chip crisis while two others duplicated work on current 2025 supply chains." Fixes were prompt-level: explicit objectives, boundaries, and "don't research X."
- **Cost/latency:** agents use ~4× and multi-agent ~15× the tokens of a chat; parallelism only pays off for high-value, genuinely independent subtasks. If subagent B needs A's output, parallelism "degenerates into expensive serial execution."
- **Review loops that never converge:** the reason every serious 2026 loop writeup converges on three hard stops — max iteration count, no-progress detection, and a token/dollar ceiling. Kiro's `max_iterations` cap (≤10) is exactly this.
- **The "just use one agent with a good loop" counterargument** is credible for a small squad. LangChain's own "3 Years of Graph Engineering" notes GPT Researcher moved *away* from a hardcoded graph toward an emergent loop; and LangChain's "how and when to build multi-agent systems" reconciles Anthropic vs Cognition as: parallelize read-heavy/breadth-first work, keep write-heavy/interdependent work single-threaded.
- **The graph-engineering discourse itself is young and partly hype.** The term crystallized from Peter Steinberger's July 18, 2026 tweet ("Are we still talking loops or did we shift to graphs yet?", ~3M views); coverage (explainx.ai, TrueFoundry, Data Science Dojo, Prefect) is largely conceptual. Treat "graph engineering" as a useful framing, not a mandate.

## Recommendations

**Stage 0 — Don't build a harness yet. Prove value with what you have.**
Run the two minimum-viable graphs below inside Kiro before writing any orchestration code. Benchmark: track tokens/credits per completed task and first-pass acceptance rate. If a single Kiro agent with good steering already hits your quality bar, stop here — the Cognition position applies to you.

**Minimum viable DESIGN graph (do this first):**
Adopt spec-driven development as a 3-node linear graph with a human gate: **requirements → design → tasks**, each a durable markdown artifact, with *you* as the approval gate between design and tasks. Use Kiro's native `/spec` flow (you already have it) or, for agent-portability and the `/analyze` consistency gate, GitHub Spec Kit. Add a single **critic node** (Kiro coach agent, or the ADK llm-auditor pattern) that reviews the design doc against explicit criteria before you approve. This is low-cost, high-inspectability (everything is a file), and matches where multi-agent structure is safest.

**Minimum viable BUILD graph (add second):**
A bounded **generator → reviewer loop**: implementer produces a change, reviewer checks against explicit criteria and emits `NEEDS_CHANGES` until it passes, `max_iterations` = 3. In Kiro, this is the native sub-agent review loop or the player/coach repo (github.com/094459/kiro-player-coach) — copy it directly. Isolate any parallel build agents with **git worktrees** from day one. Keep sub-agents read-only where possible (Cognition's rule).

**Add only when the simple version measurably hurts:**
- *You cannot debug a failed run / cannot resume from a failed edge* → this is the trigger to move the graph into **LangGraph** (per-superstep checkpointing, time-travel, resume) and wire **Langfuse or Laminar** (open-source, OTel-native) for tracing. This directly fixes the Kiro opacity complaint. Keep Kiro/`kiro-cli --no-interactive` as leaf executor nodes if you value its coding output — but budget for parsing text output until issues #5423/#9066 land.
- *Runs span hours or must survive crashes* → put **Temporal** underneath as the durable substrate; keep the agent logic in LangGraph or the vendor SDK.
- *Design work needs breadth* → widen to an **orchestrator-worker** fan-out (Anthropic pattern) for research/prior-art only, with 3–5 workers max and explicit non-overlapping boundaries.
- *You want governance/audit across the squad* → evaluate **Kiro Crew** (audit logs, approval gates, worktree app) — but know the harness stays a black box.

**Thresholds that should change your mind:**
- Token/credit cost per task >5× your single-agent baseline with no quality gain → collapse the graph back toward one agent.
- Review loop hits `max_iterations` regularly without converging → the criteria are wrong or the task is too big; fix the spec, don't add nodes.
- Parallel build agents produce merge conflicts you spend more time resolving than the parallelism saved → serialize, or enforce clean file ownership per worktree.

## Caveats
- **"Graph engineering" is a ~1-month-old framing (July 2026).** Much of the coverage is conceptual/marketing (explainx.ai, TrueFoundry, KuCoin/36Kr reposts of the Steinberger tweet). The durable engineering underneath — orchestration DAGs, checkpointing, reflection loops — predates the term by years. Weight primary repos and first-party docs over the trend pieces.
- **Kiro's sub-agent DAG has no authored graph artifact to copy** — it is agent-planned at runtime. You cannot version-control the graph itself, only the per-agent configs and your prompts. This is inherent to the current design, not something you can configure around.
- **The Anthropic 90.2% figure is for research, not coding.** Anthropic and Cognition agree coding is *less* suited to parallel multi-agent work than research. Don't over-generalize the research win to your build graphs.
- **Vendor comparison snippets (framework "showdowns," observability rankings) are partly SEO content** and several are authored by vendors ranking themselves (e.g. Laminar's own rankings). Treat feature claims as starting points and verify current version behavior — the frameworks change monthly.
- **Some cited numbers are single-practitioner data points** (e.g. the 4.3-credit player/coach iteration, "12 tasks across 5 phases") — directionally useful, not benchmarks.
